# 🏥 Medical-RAG: 高可靠医疗辅助诊疗系统

## 📑 项目描述 (Project Overview)
**一句话总结**：本项目是一个面向垂直医疗领域，具备实体级知识溯源与多轮诊断追踪能力的专家系统。
**业务场景**：旨在解决传统通用大模型在严肃医疗问答中面临的“缺乏循证依据（幻觉）”、“专有名词词汇鸿沟”、“长文本检索碎片化”及“多轮问诊意图漂移”等落地痛点。
**核心能力**：涵盖高可用离线知识库构建、实体感知嵌套分块、Dense+Sparse 多路混合召回与 RRF 融合、交叉编码器置信度截断、绝对坐标长文本重组（Small-to-Big）、以及基于 Few-Shot 的大模型智能路由与查询重写。

## 🤖 模型基座选型 (Model Stack)
- **Embedding 模型 (稠密向量)**：`BAAI/bge-m3`，支持多语言与长文本的高维语义映射。
- **Sparse 索引 (稀疏向量)**：`BM25` + `jieba` 分词，构建本地倒排索引，弥补医疗专有名词字面匹配短板。
- **Reranker 模型 (交叉精排)**：`BAAI/bge-reranker-v2-m3`，基于 Cross-Encoder 输出绝对 Logits 关联分数。
- **LLM 中枢 (生成与重写)**：`DeepSeek-V4` ，使用DeepSeek-Chat API，承担逻辑推理、格式化输出与意图提取任务。

## 👨‍💻 核心技术贡献 (Core Contributions)
*系统全链路技术决策与优化*

1. **数据接入层构建高可用幂等性数据管道与本地倒排索引**
   针对大规模向量化易触发 API 限流的痛点，设计了基于**“指数退避重试+ 文本 MD5 哈希”**的离线流。配合 ChromaDB 的 Upsert 机制实现幂等性写入，支持完全免干预的断点续传。同时将 BM25 序列化对象与原始文档深度绑定并持久化至本地，将系统在线启动耗时从 `O(N)` 降至 `O(1)`。

2. **切分策略层设计实体感知的嵌套分块算法**
   摒弃传统的固定滑动窗口切分策略。设计**“硬边界实体隔离 + 软边界递归字符切分”**的嵌套规则。在切分时强制捕获医学实体名称，并向所有子 Chunk 无差别注入包含 `【实体名称】+【绝对坐标序号】` 的强结构化 Metadata 标签，从源头解决长文本切分导致的语义孤儿问题。

3. **检索排序层实现基于 RRF 融合与 Logits 阈值截断的漏斗召回**
   构建了 `Top-30` 粗排到 `Top-10` 精排的检索漏斗。首先利用 **RRF（倒数排名融合）** 算法抹平 Dense 与 Sparse 双路的异构分数差异；随后在 Cross-Encoder 精排阶段，提取模型输出的无界 Logits 绝对分数，设定物理置信度及格线。对 OOD（库外提问）实施毫秒级硬拦截，显著降低无关 Context 导致的大模型幻觉率与 Token 成本。

4. **意图控制层提出基于全局记忆与 Few-Shot 的Query Rewrite 引擎**
   在检索前置位解耦出独立的 LLM 路由节点。为解决多轮对话架构中“长线失忆”与“话题混淆”的经典悖论，**主动摒弃了传统的滑动窗口物理截断，采用“全量历史视野+ Few-Shot 学习”范式**。通过向 LLM 注入正反对抗示例（标准指代消解 vs 强烈话题切换强制剥离），利用大模型的自注意力机制精准锚定真实意图，在保留无损长程记忆的同时，彻底压制了多轮跳跃提问时极易引发的“上下文粘连（Context Bleeding）”现象。

## 🧗‍♂️ 核心架构难点与解决方案 (Challenges & Solutions)

**难点 1：长文本检索召回后的“语义撕裂”与“N-Chunk 乱序重排”问题**
* **挑战**：一份完整的疾病指南（包含病因、症状、药物）通常会被切分为多个 Chunk。在 Rerank 精排阶段，模型严格根据 Semantic Score 排序，极易导致尾部 Chunk（如具体用药）得分高于头部 Chunk，造成喂给大模型的上下文发生“逻辑倒装”，干扰 LLM 的因果推理。
* **解决方案**：引入基于局部 Metadata 的 **Small-to-Big（子块到父块）动态聚合架构**。在检索器返回高分切片后，不直接投递给大模型，而是在内存构建哈希表，通过提取前期切分时注入的 `[绝对坐标序号]`，强制进行 `O(N log N)` 的空间位置升序排序。以细粒度切片（Small）迎合检索模型的精确召回，以绝对物理坐标还原完整拓扑（Big）迎合大模型的宏观理解，彻底消除了长文本 RAG 的乱序顽疾。

**难点 2：业务严谨性护栏与“部分命中”场景下的逻辑死锁**
* **挑战**：严肃医疗系统通常设有“未找到依据直接拒答”的安全护栏。但面对复合型 Query（如“推荐用药及居家备药方法”）时，若知识库仅命中“推荐用药”而无“备药指导”，生硬的安全护栏会导致大模型触发全局拒答机制，引发前后回答矛盾的逻辑死锁。
* **解决方案**：引入 **分级响应机制** 进行 Prompt 软路由重构。在系统指令中明确区分“完全不命中”、“局部命中”与“日常闲聊”三态。规定在局部命中时，优先提炼已知文献，缺失部分允许 LLM 调用内部医学常识（如“处方药严禁私自备药”）进行防御性建议，并解除全局拒答锁定。实现了系统在苛刻安全边界下的高情商交互。

## 📂 目录结构 (Project Structure)

```text
Medical-RAG/
├── core/                       # 核心业务逻辑模块
│   ├── document_ops.py         # 文档加载、清洗、上下文感知与坐标切分
│   ├── embedding_ops.py        # Embedding 模型接口
│   ├── vector_store.py         # ChromaDB 向量数据库持久化与 MD5 Upsert
│   ├── retriever.py            # BM25 + Dense 混合检索与 RRF 算法实现
│   ├── reranker.py             # Reranker 精排与 Threshold 置信度截断
│   └── llm_generator.py        # LLM 主生成器与 Few-Shot Query Rewrite 引擎
├── data/                       # 原始疾病及医疗 txt 数据集文件夹
├── requirements.txt            # 项目依赖包清单
├── build_index.py              # 离线全量构建脚本 (带防限流与重试机制)
└── web_app.py                  # Gradio 6.0 多模态企业级 Web 交互工作台
```

## 🛠️ 操作步骤与使用说明 (Quick Start)
1. **环境准备**
确保您的 Python 版本为 3.10+，克隆项目后安装依赖：
pip install -r requirements.txt
2. **配置 API 密钥**
在项目build_index.py,web_app.py文件下填入您的 API Key：
SILICONFLOW_API_KEY="您的硅基流动密钥"
DEEPSEEK_API_KEY="您的DeepSeek密钥"
3. **构建离线知识库**
运行离线脚本，系统将读取 data/ 目录下的文献，进行切分、调用 Embedding 模型向量化，并在本地生成 ChromaDB 向量库与 BM25 序列化索引。
python build_index.py
4. **启动 Web 辅助诊疗工作台**
python web_app.py
启动成功后，在浏览器中访问控制台输出的本地地址（默认：http://0.0.0.0:7860）即可体验包含参数动态调优、知识溯源面板的完整前端工作台。
